# 🌤️ 오늘의 진짜 정보판

> **데이터가 정상적으로 들어오지 않아도, 마지막으로 확인한 진짜 정보를 보여준다.**

부산의 현재 기온을 실제 공개 데이터에서 조회하고,
외부 데이터에 문제가 발생하더라도 **마지막 정상값을 유지할 수 있도록 만든 날씨 정보판**입니다.

| ---------- | ---------------------------------------------------- |
| 📍 대상 지역   | 부산                                                   |

| 🔄 복구      | 정상 데이터 재수신 시 `fresh` 상태로 복구                          |
| 🧪 검증      | 화면의 예외처리 검증 버튼으로 직접 재현                               |

## 🎯 프로젝트 소개

날씨 정보를 보여주는 것은 어렵지 않습니다.

하지만 **외부 API에서 데이터가 들어오지 않는다면 어떻게 해야 할까?**

이 프로젝트에서는 단순한 날씨 조회 기능보다
**데이터가 실패했을 때도 사용자가 마지막으로 확인한 정상 정보를 잃지 않는 것**에 초점을 맞췄습니다.

정상적인 상황에서는 실제 Open-Meteo 데이터를 조회하고,

```text
오늘의 날씨
부산의 현재 날씨 정보

2026-09-15
25.6°C

어제와 비교
어제(2026-09-14)보다 -1.9°C
```

데이터 조회에 실패하면 새로운 값을 잘못 표시하는 대신
**마지막 정상값을 유지하고 오류 상태를 함께 표시**합니다.

---

## 🌡️ 실제 데이터

프로젝트에서는 서로 다른 날짜에 실제 Open-Meteo 데이터를 조회하여 일별 기록을 만들었습니다.

| 날짜         |      실제 기록 |
| ---------- | ---------: |
| 2026-09-14 | **27.5°C** |
| 2026-09-15 | **25.6°C** |

따라서 2026-09-15에는 전날과 비교하여:

> **-1.9°C**

로 표시됩니다.

같은 날짜에 여러 번 조회하더라도 날짜를 기준으로 기존 기록을 갱신하기 때문에
하나의 날짜에 여러 개의 중복 기록이 쌓이지 않습니다.

## 🛡️ 데이터 장애 대응

외부 데이터는 언제든 실패할 수 있다는 것을 전제로 구현했습니다.

### 대응하는 장애 상황

```text
┌──────────────────────────────┐
│        외부 데이터 조회       │
└──────────────┬───────────────┘
               │
        정상 데이터인가?
          ┌────┴────┐
         YES        NO
          │          │
          ▼          ▼
       새 기록     오류 상태
          │          │
          │          ▼
          │      마지막 정상값
          │         유지
          │          │
          └────┬─────┘
               ▼
          사용자에게 표시
```

### 지원하는 오류

* ⏱️ Timeout
* 🔐 401/403 인증 오류
* 🚦 429 요청 제한
* 📡 Offline
* ⚠️ 응답 구조 오류

오류가 발생하면:

**새로운 잘못된 값으로 덮어쓰지 않고 → 마지막 정상값을 유지 → 오류 상태를 표시**

하는 방식으로 처리합니다.

## 🧪 예외처리 검증

평가자가 실제 네트워크를 끊거나 API를 고장 낼 필요가 없도록
페이지 안에 **「예외처리 검증」** 영역을 만들었습니다.

버튼을 클릭하면 실제 fixture 데이터를 이용해 해당 상황을 재현합니다.

| 버튼       | 재현하는 상황           |
| -------- | ----------------- |
| 정상 조회    | 실제 Open-Meteo API |
| Timeout  | 응답 시간 초과          |
| 인증 오류    | 401 / 403         |
| 요청 제한    | 429               |
| 오프라인     | 네트워크 연결 없음        |
| 응답 구조 오류 | 잘못된 응답 구조         |
| 복구 테스트   | 정상 데이터로 복구        |

### 검증 흐름

```text
정상 조회
   ↓
정상 데이터 저장
   ↓
장애 상황 발생
   ↓
마지막 정상값 유지
   ↓
오류 상태 표시
   ↓
복구 테스트
   ↓
fresh 상태로 복구
```

즉, **장애를 재현하는 것에서 끝나지 않고 복구 과정까지 확인할 수 있습니다.**

## 🧩 데이터 표준화

외부 API의 데이터를 그대로 화면에 사용하는 대신
`adapter.js`에서 프로젝트에서 사용할 표준 형태로 변환합니다.

```text
Open-Meteo API
      │
      ▼
  adapter.js
      │
      ▼
표준화된 Reading
      │
      ├── 기온
      ├── 측정 시각
      ├── 조회 시각
      ├── 시간대
      ├── 출처
      └── 기록 날짜
```

이를 통해 데이터의 출처와 시간 정보를 함께 관리할 수 있도록 했습니다.

## ✅ 검증 방법

### 1. 정상 데이터 확인

`정상 조회` 버튼을 눌러 실제 Open-Meteo 데이터를 조회합니다.

### 2. 장애 상황 확인

다음 버튼을 차례대로 눌러 각 장애 상황을 확인합니다.

```text
Timeout
인증 오류
요청 제한
오프라인
응답 구조 오류
```

### 3. 마지막 정상값 확인

오류가 발생했을 때 새로운 값으로 바뀌지 않고
**마지막으로 저장된 정상값이 유지되는지 확인합니다.**

### 4. 복구 확인

`복구 테스트` 버튼을 눌러

```text
stale → fresh
```

로 정상 복구되는 흐름을 확인합니다.

### 5. 실제 API 재확인

`정상 조회`를 눌러 실제 Open-Meteo 데이터가 다시 정상적으로 표시되는지 확인합니다.

## 💡 이 프로젝트에서 중요하게 생각한 것

### 단순히 데이터를 보여주는 것보다

**데이터가 실패했을 때 사용자가 무엇을 보게 되는가?**

에 집중했습니다.

외부 API에 의존하는 서비스에서는
정상적인 응답만을 가정하기 어렵습니다.

그래서 이 프로젝트에서는

> **정상 데이터 → 저장 → 장애 발생 → 마지막 정상값 유지 → 복구**

라는 흐름을 직접 구현하고,
평가자가 별도의 환경 조작 없이 이 흐름을 확인할 수 있도록 만들었습니다.
